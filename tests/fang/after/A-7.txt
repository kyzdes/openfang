SITE 2 CHECK — agent_loop.rs ModelNotFound fallback chain (not exercised by A-7.sh)
==================================================================
Code path confirmed by reading verify/sprint1:

  kernel.rs (both send-message paths, streaming and non-streaming):
      let mut manifest = entry.manifest.clone();
      self.apply_fallback_base_urls(&mut manifest);   // NEW
      ...
      run_agent_loop(&manifest, ...) / run_agent_loop_streaming(&manifest, ...)

  apply_fallback_base_urls() mutates manifest.fallback_models[i].base_url in
  place via the same effective_fallback_base_url() helper used by resolve_driver
  (kernel.rs:5817-5824), i.e. same-provider-as-default -> inherit dm.base_url,
  different provider -> [provider_urls] lookup, explicit base_url always wins.

  agent_loop.rs complete_with_retry (~L1327-1335) and stream_with_retry
  (~L1533) still do exactly:
      base_url: fb.base_url.clone(),
  with nothing else -- unchanged by the patch. But since they read from
  `&manifest.fallback_models` on the SAME `manifest` value that already went
  through apply_fallback_base_urls, fb.base_url is no longer None for a
  same-provider-as-default or catalog-known fallback: the patch baked the
  resolved value in before the manifest ever reached agent_loop.

  => Site 2 is fixed, but by pre-resolving the field the ModelNotFound branch
     reads, not by touching agent_loop.rs itself. This matches option 2 that
     the baseline's PATCH TARGET section proposed ("make FallbackModel carry a
     resolved base_url populated once in the kernel").

STRUCTURAL CAVEAT (could not get a clean live trigger for this exact branch):
  resolve_driver() ALSO iterates manifest.fallback_models (kernel.rs:5788ff)
  and folds every one that builds successfully into the SAME FallbackDriver
  chain as the primary. Since apply_fallback_base_urls now makes create_driver
  succeed for fallbacks that used to fail-to-construct, manifest fallbacks are
  in practice consumed by resolve_driver's chain before a request can even
  reach the ModelNotFound-classified branch inside agent_loop.rs's own retry
  loop -- that second loop only fires on the residual case where resolve_driver
  returned a bare primary (no wrapper) yet the manifest still carries
  fallback_models, or where the whole wrapped chain's last error is itself
  ModelNotFound. A live attempt to force exactly that combination (bogus
  primary model against the real hyperfusion host, y7router fallback with no
  base_url) was answered by resolve_driver's own FallbackDriver chain instead
  (driver_index=0 -> 1, see log line below) -- i.e. site 1's fix, not site 2 --
  because the fallback is already inside that chain:
    WARN openfang_runtime::drivers::fallback: Fallback driver failed, trying
         next driver_index=0 model=totally-bogus-model-xyz-999
         error=API error (401): ...key_model_access_denied...
    response: {"model_used":"kimi/k3","provider_used":"y7router","response":"PONG"}
  So: code reading gives a definite yes (the field the branch reads is no
  longer None), but no independent HTTP-level trigger of that specific branch
  was found to confirm it end-to-end at runtime; treat the "site 2 fixed" claim
  as code-proof, not behavior-proof.

CREDENTIAL-RESOLUTION DIVERGENCE (baseline noted this as a further, distinct
issue -- NOT part of the A-7 pass/fail metric, NOT fixed by this patch):
  agent_loop.rs's ModelNotFound branch still resolves the fallback API key via
      std::env::var(env_name).ok()
  bypassing resolve_credential (vault -> dotenv -> env). Confirmed live: on
  this staging container, `docker exec openfang-staging printenv
  HYPERFUSION_API_KEY` returns empty -- the key lives only in
  /var/lib/docker/volumes/openfang-staging-data/_data/secrets.env, loaded into
  the daemon's OWN process environment at startup (dotenv), not exported to
  the container's environment for freshly exec'd processes. Whether
  std::env::var() inside the already-running daemon process sees it depends on
  how that dotenv load was done (env::set_var vs. a private table) -- not
  verified here, and orthogonal to this patch, which does not touch that line.
