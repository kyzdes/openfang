=============================================================
Recon task: measure and record the red state, do not fix.

1. WHERE THE LIMIT IS
----------------------
Not in file_read itself. tool_file_read() (tool_runner.rs:1379-1388) does
a plain `tokio::fs::read_to_string(&resolved)` — no cap, no streaming, no
partial read. Its tool schema (tool_runner.rs:571-580) takes ONLY "path":

    571:            name: "file_read".to_string(),
    572-            description: "Read the contents of a file. Paths are relative to the agent workspace.".to_string(),
    573-            input_schema: serde_json::json!({
    574-                "type": "object",
    575-                "properties": {
    576-                    "path": { "type": "string", "description": "The file path to read" }
    577-                },
    578-                "required": ["path"]
    579-            }),
    580-        },

No offset, no limit, no range — grep confirms no such key anywhere in the
schema.

The actual cut is applied generically to EVERY tool result (not just
file_read) one layer up, in crates/openfang-runtime/src/context_budget.rs:

    per_result_cap()        = 30% of context_window_tokens, at an assumed
                               2.0 chars/token for "dense" tool content
                             ⇒ cap_chars ≈ 0.6 * context_window_tokens

    truncate_tool_result_dynamic(content, budget):
      if content.len() <= cap: return unchanged
      else: cut at the last '\n' at-or-before cap, append:
        "[TRUNCATED: result was {orig_len} chars, showing first {kept}
          (budget: {30}% of {window/1000}K context window)]"

Call site: crates/openfang-runtime/src/agent_loop.rs:1053 (and the
duplicate loop body at :2320), executed right after every tool call
completes, before the tool_result is appended to message history.

For this agent's 131K-token context window:
    cap = 0.30 * 131072 * 2.0 = 78643.2 chars (~78643)
Observed kept length after the newline-boundary backoff: 78483 chars
(consistent with the code walking back to the nearest '\n', losing up to
~200 chars below the raw cap).

  truncation marker found in raw tool_result:

     (budget: 30% of 131K context window)]
  actual visible prefix before the marker: 78483 bytes = 66.8% of the

  last 200 bytes actually delivered to the model, decoded for display
  (repr):
    'у других. Следующий тогда вопрос Юлия задаёт. А если цветочный
    магазин приобретен уже готовый полгода назад.'

  (minor, separate observation: the marker's own label is wrong — it

So the marker IS present verbatim in what the model reads. The model's
own hidden reasoning (captured in the same session log) shows it notices
this correctly:

  assistant turn 1 (thinking): "The file is huge, truncated. We need the
    length of the result (the entire file). The tool returned truncated
    output due to budget. It says result was 117517 chars, showing first
    78483 (budget...). So ..."

  assistant turn 2 (thinking): "Again truncated. We need last 200
    characters. Perhaps we can read the file with a different tool: maybe
    file_read supports offset? Not indicated. Alternative: Use file_list
    to see file size? Not help[ful]..."
    → confirms independently, from the model's own investigation, that
      there is no offset/limit workaround (matches section 1/4).

  final answer returned to the caller, BOTH independent runs:
    Run A (2026-08-13, pre-existing session): "117517\n…[не удалось
      получить последние 200 символов из‑за ограничения инструмента]"
    Run B (2026-08-14, tests/fang/FANG-45.sh, fresh run):     "117517  \n
      (не удалось получить последние 200 символов из‑за ограничения
      инструмента)"

Both times the model reports 117517 — the file's TOTAL size, taken
straight out of the truncation marker's "result was N chars" clause — as
if that many characters had reached it, when it actually received 78483.
It never states 78483, never states 66.8%, never tells the caller "I only
got part of the file." The disclosure exists in the raw tool output but
does not survive translation into the model's own summary. From the
calling side (a user, or another agent consuming this agent's answer)
this is indistinguishable from file_read silently returning a partial
file: the reported byte count is wrong and overstates completeness by
39034 bytes (33.2%).

4. IS THERE A WORKAROUND (offset/limit)?
------------------------------------------
No. Confirmed two ways:
  a) Source: file_read's JSON schema (tool_runner.rs:571-580) has exactly
     one parameter, "path". No offset/limit/range key exists anywhere in
     builtin_tool_definitions() for file_read.
  b) Live: the model itself searched for a workaround in its own
     reasoning ("maybe file_read supports offset? Not indicated") and
     found none, then gave up on retrieving the last 200 characters
     rather than guessing.
This is itself part of the defect: even an agent that correctly detects
the truncation has no tool-level way to page through the rest of a large
file. The only escape hatches are shell_exec (if the hand allows it,
e.g. `tail`/`sed` on the workspace file) or splitting the source file
before ingestion — neither is file_read's job, and neither is suggested
anywhere in file_read's own description or error text.
